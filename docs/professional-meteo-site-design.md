# 专业静态气象工具站设计规格

## 1. 目标定位

将现有静态 HTML 工具页升级为一个面向气象值班人员的专业气象业务网站。第一阶段保持 GitHub Pages 静态部署和无构建工具形态不变，重点提升首页入口、信息架构、专业表达、使用路径、状态反馈和页面一致性。

站点定位为：

- 面向机场气象值班、趋势研判和运行参考的业务工具站。
- 基于公开数值预报、机场基础资料和理论计算结果提供辅助参考。
- 不作为航班放行、签派、运行标准或精密天文计算的唯一依据。

第一阶段不引入账号、后台数据库、服务器、React/Vue 构建链或复杂权限体系。

## 2. 页面角色

### `/` 工具首页

`index.html` 作为网站首页，不承载复杂业务图表脚本。

核心角色：

- 使用类似微软悬浮磁块的入口样式展示业务工具。
- 用户点击磁块进入精细化预报、多尺度趋势研判或日照参考。
- 首页保持轻量，降低首次访问时的脚本和接口加载压力。

### `/index1` 精细化机场预报工作台

原 `index.html` 的精细化预报功能迁移为 `index1.html`，作为独立工具页。

核心角色：

- 输入机场四字码后查看未来 7 天逐小时精细化天气预报。
- 支持温度、露点、降水、风、云量、湿度、气压等核心要素查看。
- 提供最常用的短期值班参考入口。

第一阶段页面应保持：

- 专业页面标题和副标题，明确时间尺度与适用范围。
- 数据源、机场库和图表依赖状态提示。
- 业务免责声明，统一表达“数值预报结果仅供值班参考”。

### `/index2` 多尺度趋势研判

现有 `index2.html` 定位为多时间尺度天气趋势研判页。

核心角色：

- 精细化预报用于 0-7 天短期查看。
- 集合预报用于 0-15 天不确定性和趋势判断。
- 延伸期预报用于 15-45 天背景趋势参考。
- 季节预报用于 1-6 个月背景形势参考。
- 气候预估用于历史和未来气候背景参考。

第一阶段页面应增加：

- 与首页一致的站点导航和专业标题。
- 五类数据源独立状态继续保留，并在视觉上形成稳定信息区。
- 每个时间尺度的业务解释，帮助用户判断“能看什么、不能直接拿来做什么”。
- 自定义气候查询失败时展示具体错误，避免笼统提示。

### `/index3` 机场日照与昼夜节律参考

现有 `index3.html` 定位为机场日出日落和日照时间参考页。

核心角色：

- 输入机场四字码和年份，生成全年日出日落时间表。
- 支持 UTC 和 LT 两种显示方式。
- 自动定位机场当地日期的今天。
- 提供值班排班、季节变化、昼夜节律和日照时长参考。

第一阶段页面应增加或保留：

- 与其他页面一致的站点导航。
- 算法说明、更新说明、数据来源说明保持分开展示。
- 明确说明已考虑经纬度、机场时区和可用标高近似修正。
- 明确说明未校正周边山体、建筑物遮挡和实时大气折射。

## 3. 全站信息架构

第一阶段采用“首页 + 三个工具页”的静态网站结构：

- `/`：工具首页。
- `/index1`：精细化机场预报工作台。
- `/index2`：多尺度趋势研判。
- `/index3`：机场日照与昼夜节律参考。

首页提供磁块入口：

- 精细化预报。
- 多尺度研判。
- 日照参考。

工具页可提供轻量返回首页或跨页面入口，但不应挤压原有查询、图表和日历主功能。

## 4. 统一 UI 原则

整体风格应偏专业业务工具，而不是营销落地页：

- 信息密度适中，优先便于值班人员快速扫描。
- 深色或沉稳中性色可用于主工作区，但避免单一蓝色或紫色堆叠。
- 工具页的按钮、输入框、状态标签和说明块保持一致。
- 卡片仅用于独立信息块，不做大面积装饰卡片嵌套。
- 移动端允许缩放，布局应避免横向溢出。
- 页面说明文字使用小字号和低强调，不干扰核心图表或查询操作。

## 5. 统一业务文案

推荐统一免责声明：

> 本工具基于公开数值预报、机场基础资料和理论计算结果生成，仅供气象值班、趋势研判和运行参考，不作为放行、签派或运行标准的唯一依据。

推荐统一数据来源说明：

- 天气数据：Open-Meteo。
- 机场基础数据：mwgg/Airports。
- 图表渲染：Apache ECharts。
- 日出日落计算：SunCalc。

页面内说明应优先使用短句和列表，避免长段说明压过主功能。

## 6. 数据与错误处理原则

三个工具页应继续保持当前低风险容错策略：

- 机场库在线加载设置 8 秒超时。
- localStorage 保存 7 天机场库缓存。
- 在线机场库失败时优先使用有效缓存。
- 没有缓存时提示“数据库不可用”，不误导为“机场不存在”。
- 外部接口请求检查 HTTP 状态和 API 错误体。
- 核心 CDN 依赖加载失败时给出页面级明确提示。

`index2.html` 应继续对五类数据源分别显示状态，单个数据源失败不影响其他已成功数据查看。

## 7. 第一阶段实施清单

第一阶段实施范围：

- 首页承担统一入口，工具页保留轻量跨页面入口。
- 新建磁块式首页，入口指向 `index1`、`index2`、`index3`。
- 将原精细化预报保留为 `index1.html`。
- 更新工具页标题、页面定位和免责声明。
- 优化 `index2.html` 的多尺度业务解释和数据源状态区。
- 优化 `index3.html` 的 UI 风格，使其与精细化预报和多维度预报的深色业务工具界面一致。
- README 增加专业网站改造说明和页面定位。
- 回归测试增加对导航、统一免责声明和页面定位的静态断言。

第一阶段不做：

- 不引入构建工具。
- 不新增登录、用户系统、后端数据库。
- 不将公共逻辑拆为外部 JS/CSS 文件。
- 不改变现有 API 数据源。

## 8. 第二阶段预留方向

当第一阶段页面结构稳定后，再考虑第二阶段模块化：

- 抽出 `assets/common.css`，统一视觉组件。
- 抽出 `assets/common.js`，统一导航、机场库缓存、请求超时和错误提示。
- 抽出 `assets/meteo-api.js`，统一 Open-Meteo 请求封装。
- 增加常用机场和最近查询的跨页面共享。
- 增加导出图片、导出 CSV 或值班记录打印能力。

第二阶段应单独制定规格和实施计划。

## 9. 验收标准

第一阶段完成后应满足：

- 三个公开入口 `/`、`/index2`、`/index3` 仍可访问。
- 首页以磁块方式清楚展示三个工具入口。
- `/index1` 能执行机场精细化天气查询。
- `index2.html` 仍能展示五类数据源状态。
- `index3.html` 的 UTC/LT、今日定位、算法说明和更新说明仍可用。
- 静态回归测试覆盖首页入口、三个工具页主脚本语法、数据源说明和核心容错函数存在。

## 10. 发布方式

保持当前发布方式：

- 在本地修改静态文件。
- 运行静态回归测试。
- 提交到 `main` 分支。
- 推送至 GitHub。
- 等待 GitHub Pages 自动刷新。
